# MHR Scale – الإصدار 2.0.6

منصة ويب ثنائية اللغة (العربية/الإنجليزية) مبنية باستخدام React وTypeScript وVite، ومتصلة بمشروع Supabase الحالي فقط.

- Project ref: `oafvsazddiwgjjhwwgix`
- Supabase URL: `https://oafvsazddiwgjjhwwgix.supabase.co`
- لا ينشئ هذا المشروع قاعدة بيانات بديلة ولا ينفذ migrations تلقائياً.
- مجلد `supabase/migrations` يحفظ migrations الإضافية الخاصة بهذا الإصدار، وهي مطبقة بالفعل على المشروع المتصل؛ لا تعِد تنفيذها يدوياً.

## التشغيل المحلي

1. انسخ `.env.example` إلى `.env`.
2. ضع رابط Supabase ومفتاح Publishable (أو anon القديم) في متغيرات البيئة.
3. لا تضع مفتاح `service_role` أو مفتاح Brevo في الواجهة أو مستودع Git.
4. نفذ `npm install` ثم `npm run dev`.
5. تحقق من البناء باستخدام `npm run build`.

## الأدوار الستة المعتمدة

- `worker` – العامل.
- `site_safety_officer` – مسؤول السلامة بالموقع.
- `site_doctor` – طبيب الموقع.
- `review_doctor` – طبيب المراجعة.
- `occupational_health_responsible` – مسؤول الصحة المهنية العام.
- `system_owner` – مالك النظام.

لا يوجد دور مستقل للمدير المباشر؛ أُلغي من نطاق النظام بناءً على قرار صاحب المشروع. ولا يُطلب من العامل إدخال اسم المدير أو اسم مستخدمه. تبقى الموافقات ضمن الأدوار الستة أعلاه.

تقرأ الواجهة التعيينات النشطة من `mhr_role_assignments`. مالك النظام يستطيع من لوحة الإدارة استعراض حسابات Auth عبر Edge Function `mhr-admin-users`، إرسال دعوة، إسناد دور، وإيقاف تعيين. إرسال الدعوة لا يمنح صلاحية تلقائياً. إسناد الدور يخضع كذلك إلى سياسات RLS في قاعدة البيانات.

## مسارات العمل الموجودة في الواجهة

- ملف العامل المهني منفصل عن ملفه الطبي في قاعدة البيانات.
- العامل ينشئ مسودة ويضيف الأخطار ثم يرسل الملف من خلال `submit_worker_case`.
- بعد الإرسال تُقفل تعديلات العامل حتى إعادة الملف للتصحيح وفق دورة المراجعة.
- مسؤول السلامة يرى بيانات العامل المهنية والأخطار، ولا تطلب الواجهة الملف الطبي منه.
- البيانات الطبية متاحة للعامل صاحب الملف وللأطباء المخولين فقط وفق صلاحيات RLS؛ مالك النظام يدير الحسابات والبيانات التشغيلية دون وصول طبي تلقائي.
- مراجعتا السلامة والطب بالموقع تسيران بالتوازي، ثم تنتقل الحالة للمراجعة المركزية.
- مؤشر المراجعة الطبية المركزي يأخذ القيمة الأعلى بين مؤشر طبيب الموقع والقيمة التي يدخلها طبيب المراجعة.
- سجل الأحداث يعرض للمستخدمين الذين تسمح لهم سياسة قاعدة البيانات بذلك؛ لا تطلب الواجهة سجل الأحداث من مسؤول السلامة.
- قاعدة البيانات تمنع تكرار التعيين النشط نفسه، وتحمي آخر تعيين نشط لمالك النظام من الإيقاف أو الحذف.

## إعداد البيئة

المتغيرات المطلوبة:

- `VITE_SUPABASE_URL`
- `VITE_SUPABASE_ANON_KEY` – يمكن وضع Publishable key هنا رغم الاسم التاريخي للمتغير.

هذه المفاتيح العامة مخصصة للمتصفح وتظل صلاحيات البيانات محكومة بـ RLS. لا تضف `SUPABASE_SERVICE_ROLE_KEY` أو `BREVO_API_KEY` إلى متغيرات `VITE_`.

## الضوابط العلمية والطبية

- لا توجد معادلة CRI أو أوزان أو حدود تصنيف معتمدة مضمنة في التطبيق.
- H×E ترتيب أولي داخلي للأخطار ذات الدرجات الرتبية فقط؛ ليس تقييماً كمياً معتمداً ولا حد تعرض ولا قرار لياقة.
- الشدة والتعرض ووسائل التحكم والمؤشر الصحي أبعاد منفصلة.
- لا يصدر النظام قرار Fit/Unfit آلياً؛ القرار الطبي النهائي للطبيب المختص وبالاستناد إلى متطلبات الوظيفة والمرجع المعتمد.
- لا يُدّعى أن التطبيق معتمد من ISO أو NIOSH أو ILO أو أي جهة أخرى.

## النشر

يوجد `vercel.json` لإعادة توجيه مسارات SPA إلى `index.html`. يمكن كذلك تشغيل المشروع على Replit بعد إتاحة إنشاء التطبيقات. أضف متغيرات البيئة في لوحة الاستضافة، ثم اضبط Supabase Auth Redirect URLs والنطاق HTTPS.

## تحديثات الإصدار 2.0.6

- استمرار إظهار اسم المستخدم والدور النشط والموقع المرتبط بالتعيين وشريط تقدم سير الملف.
- فصل صلاحية إدارة النظام عن صلاحية الاطلاع الطبي: مالك النظام لا يحصل على الملف الطبي أو المراجعات الطبية لمجرد امتلاكه صلاحية الإدارة.
- حصر الاطلاع الطبي في العامل صاحب الملف والأدوار الطبية المخولة: طبيب الموقع، طبيب المراجعة، ومسؤول الصحة المهنية العام.
- إضافة migration لاختبارات انحدار بنيوية لسياسات سرية البيانات الطبية.
- إلغاء دور المدير المباشر يظل سارياً؛ لا توجد مرحلة اعتماد للمدير المباشر.
